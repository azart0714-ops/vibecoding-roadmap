# 🐝 МУЛЬТИАГЕНТНЫЕ СИСТЕМЫ И ORCHESTRATION SWARM ПОД УПРАВЛЕНИЕМ ИИ (ЭТАП 8)

Этот документ представляет собой глубокое архитектурное исследование и набор стандартов для построения **ройных мультиагентных систем (Swarm Orchestration)**. В условиях сложной коммерческой разработки один автономный агент неизбежно деградирует по контексту и совершает ошибки. Переход к роевой структуре с разделением ролей, формализованными протоколами передачи задач (handoffs) и долговременной памятью — это единственный путь к стабильному качеству кода.

---

## 📐 1. SWARM ORCHESTRATION: ПРОТОКОЛЫ КООРДИНАЦИИ И ПЕРЕДАЧИ ЗАДАЧ

Swarm-оркестрация базируется на концепции легких специализированных агентов, которые координируются центральным диспетчером или передают управление друг другу через строгие транзакции.

### 🔹 1.1. Протокол передачи задач (Task Handoff Protocol)
Агенты не должны общаться в свободном текстовом формате. Передача задачи от одного агента к другому сопровождается стандартизированным пакетом данных (Handoff Artifact):
1.  **Context Payload**: Текущее состояние файлов, ссылки на ключевые символы (классы, типы), история изменений.
2.  **Explicit Instruction**: Четкое описание того, что именно должен сделать следующий агент (например: *"QA-инженер, запусти авто-тест на странице авторизации"*).
3.  **Completion Criteria (DoD)**: Критерии готовности, по которым следующий агент определит успешность выполнения задачи.

### 🔹 1.2. Параллельное выполнение и циклы обратной связи (Feedback Loops)
*   **Параллельные суб-агенты**: Для ускорения рутинных задач (например, написание модульных тестов для 5 разных компонентов) диспетчер запускает параллельные сессии ИИ-разработчиков, которые работают в изолированных ветках Git.
*   **Цикл "Разработчик -> QA"**: Автоматический цикл обратной связи. Frontend-агент генерирует код и передает задачу QA-агенту. QA-агент запускает тесты. Если тест падает, QA-агент возвращает задачу Frontend-агенту вместе с логом ошибки. Цикл повторяется до тех пор, пока тесты не пройдут успешно (максимум 3-5 итераций во избежание бесконечных циклов).

## 🎭 2. СПЕЦИАЛИЗИРОВАННЫЕ РОЛИ В ИИ-КОМАНДЕ

Разделение обязанностей снижает нагрузку на контекстное окно каждого отдельного агента и повышает точность работы.

| Роль Агента | Зона Ответственности | Ключевые Инструменты |
| :--- | :--- | :--- |
| **Tech Lead (Архитектор)** | Проектирование архитектуры, декомпозиция задач, ревью кода, составление планов реализации (`implementation_plan.md`). | `grep_search`, `view_file` |
| **Frontend Engineer** | Верстка UI, логика компонентов, интеграция дизайн-систем, стилизация Tailwind CSS, стейт-менеджмент. | `write_to_file`, `replace_file_content` |
| **Backend Engineer** | Проектирование API-эндпоинтов, миграции баз данных, настройка ORM (Prisma/Drizzle), бизнес-логика. | `write_to_file`, ORM CLI |
| **QA Engineer** | Авто-тестирование, написание Unit и E2E тестов, валидация по чек-листам, верификация интерфейсов. | `run_command` (Playwright, Jest) |
| **Design Engineer** | Перенос макетов из Figma/v0.dev, создание токенов стилей, микро-анимации Framer Motion, аудит доступности (a11y). | `generate_image`, v0.dev CLI |

## 🧠 3. ДОЛГОВРЕМЕННАЯ ПАМЯТЬ И RAG ДЛЯ АГЕНТОВ

Без долговременной памяти агенты забывают архитектурные паттерны проекта, принятые соглашения и предпочтения разработчика, повторяя одни и те же ошибки из сессии в сессию.

### 🔹 3.1. Структура `agent_db.json` (База Данных Агента)
Файл `agent_db.json` хранит метаданные о состоянии проекта и выполненных шагах. Он обновляется автоматически в конце каждой сессии:
*   *Профиль проекта*: Используемые технологии, версии зависимостей, пути к ключевым файлам.
*   *Предпочтения*: Любимые паттерны разработчика (например, *"Использовать Zustand для стейта кнопок"*).
*   *Ошибки и извлеченные уроки*: Журнал багов, с которыми агент столкнулся, и методы их решения (предотвращает повторение ошибок).

### 🔹 3.2. Хронологический граф знаний (`long_term_kg.md`)
Файл представляет собой семантический граф взаимосвязей компонентов системы. Он строится на основе временных меток (Temporal Knowledge Graph):
*   Показывает, как изменение одного модуля (например, схемы базы данных) влияет на другие модули (API роуты, типы TypeScript, компоненты UI).
*   *DX-эффект*: Перед началом работы агент считывает этот граф и сразу понимает зависимости, не тратя токены на сканирование всей кодовой базы.

## 🎭 4. АВТОМАТИЗАЦИЯ ВЕРИФИКАЦИИ И ИНФРАСТРУКТУРНЫЕ ШЛЮЗЫ

Ни один код, сгенерированный ИИ, не должен попадать в основную ветку без прохождения автоматических проверок (Quality Gates).

### 🔹 4.1. Автономное E2E тестирование с Playwright
После генерации UI ИИ-агент не может глазами проверить верстку. QA-агент обязан запустить Playwright для сквозной валидации:
1.  **Проверка рендеринга**: Элементы должны успешно загружаться, скелетоны должны исчезать.
2.  **Проверка сценариев**: Авторизация, отправка форм, переключение табов должны работать без JS-ошибок в консоли.
3.  **Скриншот-тестирование**: Playwright делает эталонные скриншоты страниц и сравнивает их с новыми версиями для выявления визуального регресса.

### 🔹 4.2. Шлюзы CI/CD в GitHub Actions
Интеграция с GitHub Actions гарантирует соблюдение правил:
*   **Branch Protection**: Запретить прямой пуш в ветку `main`. Любые изменения вносятся только через Pull Requests.
*   **Автоматические проверки**: При создании PR триггерится воркфлоу: `npm run lint` -> `npm run build` -> запуск тестов Playwright/Jest.
*   **Блокировка слияния**: PR не может быть слит, если упала хотя бы одна проверка или если отсутствует аппрув от Tech Lead агента.
