## 🎯 ОСНОВНАЯ ИДЕЯ

Вайбкодинг — мощный инструмент, но без критического мышления превращает разработчика в "генератора технического долга". Статья разбирает 5 критических ошибок и способы их избежать.

---

## 📊 5 ГЛАВНЫХ ОШИБОК ВАЙБКОДИНГА

### Ошибка №1: Слепое доверие сгенерированному коду (ИИ-копипаст)

**Проблема**: Copy-Paste Driven Development — принимаем код просто потому, что он выглядит правдоподобно.

**Риски**:
- **Дыры в безопасности**: устаревшие методы хеширования, SQL-инъекции
- **Фантомные баги и галлюцинации**: несуществующие методы библиотек, миксование несовместимых версий

**Решение**: **Trust, but verify** (доверяй, но проверяй)
- Относиться к ИИ как к "гиперактивному джуну"
- Обязательное код-ревью перед коммитом
- Проверка документации сомнительных методов

**Цитата**:
> "Вы бы приняли Pull Request от стажера не вчитываясь? Вряд ли. Вот и сгенерированный код требует обязательного код-ревью."

---

### Ошибка №2: Потеря контроля над архитектурой

**Проблема**: ИИ решает локальные задачи, не понимая глобальной структуры проекта.

**Риски**:
- Проект превращается в "франкенштейна"
- Дублирование логики (прощай, DRY)
- Нарушение SOLID, циклические зависимости
- Спагетти-код

**Решение**: **Сначала архитектура, потом промпт**
- Использовать `@codebase` в Cursor для глобального контекста
- Создавать `.cursorrules` с гайдлайнами проекта
- Разносить логику по правильным слоям — это работа разработчика

**Золотое правило**:
> "Вы здесь главный инженер, а не просто оператор чат-бота."

---

### Ошибка №3: Игнорирование краевых случаев

**Проблема**: **Happy Path Syndrome** — ИИ пишет код для идеального мира.

**Риски**:
- Код падает на невалидных данных (эмодзи вместо телефона)
- Нет обработки таймаутов API
- Отсутствие проверок на `null`/`undefined`
- Нет `try/catch` блоков

**Решение**: **Defensive Prompting** (защитные промпты)
- Добавлять "хвосты" в запросы: _"Учти краевые случаи (edge cases), добавь строгую валидацию входящих данных и адекватную обработку ошибок"_
- Заставлять ИИ писать тесты: _"Напиши юнит-тесты для этой функции. Обязательно покрой негативные сценарии и невалидный ввод"_

**Инсайт**:
> "ИИ находит логические дыры в собственном же коде на этапе написания тестов."

---

### Ошибка №4: Деградация навыка отладки ("Бесконечный цикл промптов")

**Проблема**: Вместо анализа ошибки копируем трейсбек в чат: "Почини" → "Всё еще не работает" → бесконечный цикл.

**Риски**:
- Нейросеть суетится и вносит хаотичные изменения
- Ломает рабочий код
- Разработчик теряет ментальную модель проекта
- Деградация навыков отладки

**Решение**: **Правило двух попыток**
1. Скинули ошибку → ИИ предложил фикс
2. Не помогло? → Еще одно уточнение
3. После второго раза → **СТОП**
   - Открываем DevTools
   - Расставляем брейкпоинты
   - Вдумчиво читаем логи
   - Разбираемся самостоятельно

**Важно**:
> "Возвращаем себе контекст и контроль над кодом."

---

### Ошибка №5: "Ленивые" промпты и плохой контекст

**Проблема**: "Сделай мне форму авторизации" — без уточнений по стеку, стилям, бизнес-логике.

**Риски**:
- Дженерик-решение (классовые компоненты React 2018)
- Ненужные зависимости (Redux для двух инпутов)
- Несоответствие стеку проекта (CSS вместо Tailwind)
- Больше времени на рефакторинг, чем на написание с нуля

**Решение**: **Prompt Engineering для разработчиков**

**Формула хорошего промпта**: **Контекст + Роль + Задача + Ограничения**

**Пример**:
```
❌ Плохо: "Сделай форму авторизации"

✅ Хорошо: "Ты Senior Frontend Developer (Роль). 
Мы пишем приложение на Next.js App Router (Контекст). 
Создай клиентский компонент формы авторизации с полями email и пароль (Задача). 
Используй Tailwind для стилей, не тяни сторонние библиотеки вроде React Hook Form, 
вся валидация на уровне нативных HTML5-атрибутов (Ограничения)."
```

**Результат**:
> "Вы потратите на 30 секунд больше времени на запрос, но сэкономите часы на мучительном рефакторинге."

## 💡 КЛЮЧЕВЫЕ ИНСАЙТЫ

### 1. Вайбкодинг ≠ Замена инженерии

> "ИИ не забирает у нас работу, он забирает рутину. Но вайбкодинг — это ни в коем случае не замена полноценной инженерии. Скорее наоборот, он задирает планку требований к разработчику."

### 2. Новые навыки на первый план

Когда скорость набора текста больше не узкое место:
- Системная архитектура
- Проектирование
- Строгое ревьюирование

### 3. Челлендж для внедрения

**Правило на неделю**: Ни одного слепого `Tab` или `Accept`
- Осознанное код-ревью каждого куска логики
- Проверка перед коммитом

## 📌 ПРАКТИЧЕСКИЕ РЕКОМЕНДАЦИИ

### Чек-лист перед Accept кода:

```markdown
- [ ] Прочитал логику (не просто пробежал глазами)
- [ ] Проверил документацию сомнительных методов
- [ ] Убедился в обработке ошибок (try/catch)
- [ ] Проверил валидацию входных данных
- [ ] Убедился в отсутствии дублирования логики
- [ ] Код соответствует архитектуре проекта
- [ ] Нет устаревших/небезопасных методов
```

### Шаблон защитного промпта:

```
[Основная задача]

Дополнительные требования:
- Учти краевые случаи (edge cases)
- Добавь строгую валидацию входящих данных
- Добавь адекватную обработку ошибок
- Напиши юнит-тесты (включая негативные сценарии)
```
