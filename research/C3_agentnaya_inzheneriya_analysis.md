## 🎯 ГЛАВНАЯ ИДЕЯ

**Агентная инженерия (Agentic Engineering)** — дисциплина, которая отвечает на вопрос: как проектировать процессы, инструменты и контекст так, чтобы AI-агент работал **предсказуемо**. Не как генератор случайных сниппетов, а как управляемый участник команды.

**Ключевой тезис**: "Вместо написания кода — проектирование архитектуры, формулирование спецификаций, настройка контекста и контроль качества."

## 📚 СТРУКТУРА СТАТЬИ (6 РАЗДЕЛОВ)

### 1️⃣ Промпт-инженерия: 6 приёмов

**Принцип**: Промпт — это **спецификация**, а не пожелание.

#### 1.1. Контекст-фрейм
- ❌ Плохо: "Напиши функцию валидации формы"
- ✅ Хорошо: "Проект: Next.js 15, TypeScript strict, Zod, Prisma + PostgreSQL. Не используй any. Не добавляй зависимости. Напиши Zod-схему регистрации..."
- **Эффект**: Один абзац контекста экономит 3 итерации переписывания

#### 1.2. Пример входа-выхода
- Показывать конкретные примеры вместо описания словами
- `user@domain.com` → valid: true
- `test@` → valid: false, причина: нет домена
- **Эффект**: Модель копирует паттерн, а не интерпретирует описание

#### 1.3. Negative Prompting
- "НЕ меняй сигнатуру. НЕ добавляй зависимости. НЕ трогай /src/core/"
- **Эффект**: Каждое "не" сужает пространство решений

#### 1.4. Chunking
- ❌ Плохо: "Напиши CRUD API с авторизацией, валидацией и тестами"
- ✅ Хорошо: Разбить на шаги (типы → сервисы → ошибки → API-роуты)
- **Эффект**: При большом объёме модель теряет фокус и "срезает углы"

#### 1.5. Spec-first
- Описать контракт до реализации: POST /api/orders, тело запроса, варианты ответов
- **Эффект**: Механические задачи — то, что модель делает лучше всего

#### 1.6. Привязка к реальности
- Дать фрагмент реальной схемы/документации прямо в промпте
- **Эффект**: Лучшая защита от галлюцинаций — реальный контекст

### 2️⃣ CLAUDE.md: Онбординг для AI-агента

**Что это**: Не документация и не README. Это онбординг для AI-агента — как для нового разработчика.

#### Структура из 5 секций:
1. **Проект** — краткое описание, стек, архитектура (1 абзац)
2. **Структура директорий** — где что лежит
3. **Паттерны кода** — реальные фрагменты (не описание!)
4. **Правила** — что делать всегда
5. **Запрещено** — что не делать никогда

#### 3 ошибки, убивающие эффективность:
- **Слишком длинный** (>1000 строк) — противоречия между правилами
- **Слишком абстрактный** — "Пиши чистый код" бесполезно
- **Устаревший** — описывает прошлую архитектуру

#### Практический совет:
Начать с 50 строк. Добавлять правила по мере обнаружения ошибок. CLAUDE.md — **живой артефакт**.

#### Аналоги:
- Claude Code → `CLAUDE.md`
- Cursor → `.cursorrules`
- Windsurf → `.windsurfrules`

### 3️⃣ Model Context Protocol (MCP)

**Назначение**: Протокол взаимодействия агента с внешним миром (создавать задачи, отправлять письма, запрашивать данные).

#### Архитектура (3 роли):
- **Host** — приложение (Claude Code, Cursor, Windsurf)
- **Client** — компонент внутри хоста
- **Server** — отдельный процесс с возможностями

#### 3 примитива:
1. **Tools** — функции (создать задачу, SQL-запрос, отправить письмо) — 90% серверов
2. **Resources** — данные для чтения без побочных эффектов
3. **Prompts** — шаблоны для типовых сценариев

#### Транспорт:
- **stdio** — для локальных серверов (stdin/stdout)
- **Streamable HTTP** — для удалённых (заменил устаревший SSE)
- Под капотом: JSON-RPC 2.0

#### Критический момент:
**Описание инструмента — это промпт для модели, а не комментарий для человека.**
- ❌ "Работает с данными" — бесполезно
- ✅ "Возвращает список открытых задач проекта. Принимает статус фильтрации. Если задач нет — пустой массив" — работает

#### Практика: MCP-сервер за 5 шагов
1. `npx @modelcontextprotocol/create-server todo-server`
2. Tools с описаниями через `.describe()`
3. Resources (текущее состояние)
4. Подключение в `.mcp.json`
5. Отладка через `npx @modelcontextprotocol/inspector`

#### 3 грабли:
- Абстрактные описания
- Нет error handling
- Переусложнённые параметры (10 полей)

#### Экосистема:
- Каталог: https://github.com/modelcontextprotocol/servers
- Спецификация: https://spec.modelcontextprotocol.io

### 4️⃣ Git Worktrees

**Проблема**: Агент занят долгой задачей в одной ветке, а нужно параллельно работать в другой.

**Решение**: Git worktree — дополнительная рабочая копия того же репозитория, привязанная к другой ветке. Один `.git`, несколько директорий.

#### Зачем AI-разработчику:
- **Параллельные сессии** — агент в `feature/auth`, вы в `feature/api`
- **Изолированные эксперименты** — радикальный рефакторинг без риска
- **Code review** — проверка PR без прерывания основной работы

#### Команды:
```bash
git worktree add ../my-project-feature feature/new-api
git worktree list
git worktree remove ../my-project-feature
```

#### В Claude Code:
Встроенная поддержка через Task tool с `isolation: "worktree"` — автоматическое создание временного worktree для подзадач.

#### Практический паттерн:
```
~/projects/my-app/          # main
~/projects/my-app-feature/  # feature/new-api
~/projects/my-app-hotfix/   # hotfix/critical-bug
~/projects/my-app-review/   # review/pr-123
```

### 5️⃣ Паттерны ошибок AI-кода

**Тезис**: AI-генерация порождает не больше багов, но **паттерны другие**.

#### 5.1. Галлюцинации API
- Пример: `prisma.user.findByEmail()` — метода не существует
- Правильно: `findUnique({ where: { email } })`
- **Защита**: Strict TypeScript

#### 5.2. Устаревший синтаксис
- `componentDidMount` вместо `useEffect`
- `var` вместо `const/let`
- `new Buffer()` вместо `Buffer.from()`
- **Защита**: Явно указать в CLAUDE.md: "React только хуки. Node.js >= 20"

#### 5.3. Security-дыры
- SQL-инъекция (прямая подстановка в SQL-строку)
- XSS (`innerHTML = userInput`)
- Path traversal (`fs.readFile(userInput)`)
- Command injection (`exec(userInput)`)
- **Проблема**: AI оптимизирует на "работает", а не на "безопасно"

#### 5.4. Happy Path Only
- Забывает `null`/`undefined`
- Пустой массив → `items[0].name` упадёт
- Сетевые таймауты без AbortController
- Race conditions
- **Проблема**: Модель пишет код для идеального мира

#### 5.5. Phantom Dependencies
- AI импортирует пакет, которого нет в npm
- Пример: `json-schema-validator-pro` — выдумка
- **Опасность**: Атакующие регистрируют такие имена (dependency confusion)
- **Защита**: `npm info` перед установкой

#### Как ловить систематически:
1. **Strict TypeScript + ESLint** — первая линия обороны
2. **AI vs AI** — один пишет, другой ревьюит
3. **npm audit + npm info** — проверка зависимостей
4. **CLAUDE.md с запретами** — снижает повторение ошибок на порядок

### 6️⃣ Мульти-агентные воркфлоу

**Проблема**: Один агент не может быть архитектором, кодером, тестировщиком и техписом одновременно.

**Принцип**: Чем уже задача — тем точнее результат.

#### Паттерн 1: Pipeline (конвейер)
```
Architect → Coder → Reviewer → Tester
```
- Каждый видит только свой кусок контекста
- Изолированный контекст = работа строго в своей роли

#### Паттерн 2: Router + Specialists
```
Router → [DB Agent | API Agent | UI Agent | DevOps Agent]
```
- Router анализирует задачу и направляет к специалисту
- Каждый имеет узкий контекст (DB Agent знает схему, UI Agent — дизайн-систему)

#### Паттерн 3: Adversarial (состязательный)
```
Generator ↔ Critic → итоговый результат
```
- Generator пишет код
- Critic ломает (edge cases, race conditions)
- Generator исправляет
- 2-3 итерации находят баги, которые ручное ревью пропускает

#### Реализация в Claude Code:
- Task tool — запуск подзадачи в чистом контексте
- Подагент не видит историю основного разговора
- Обмен через файлы (spec.md, код, тесты)
- В сочетании с git worktrees — каждый агент в изолированной копии

#### Когда это оверинжиниринг:
**Правило**: Если задача декомпозируется на роли — используйте мульти-агентный воркфлоу. Если нет — одного агента достаточно.
